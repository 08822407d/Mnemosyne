## 1. 背景与用途

一个长期项目以 **Git 仓库中的 Markdown/YAML 文件**为唯一长期真相源（当前量级：数百文件、约数 MB 纯文本，持续增长），原则是"记录≠加载"：保存尽量全，但每次会话只加载最小充分集。现状靠人工维护的分层加载表（核心集＋条件触发集）调度，无向量检索层。已知外部证据表明：统一测试下外部键值/稠密检索是很强的基线，但相似度检索会丢因果与状态信息。本研究为"要不要建检索层、建哪种、维护代价多大"这一具体设计决定采集证据。

## 2. 研究问题（逐题回答）

**Q1 · 中小规模文本库的检索实证**：对 <10~50MB 纯文本知识库，关键词/grep/BM25、结构化索引（目录＋登记表）、embeddings、hybrid 四类方案在 2025-2026 的实证比较结论；"规模多大之前根本不需要向量"这类阈值证据。

**Q2 · coding-agent 生态的按需加载机制盘点**：Claude Code（分层 rules、子目录按需加载、auto-memory 分页）、Cursor rules、GitHub Copilot instructions、AGENTS.md 生态等；触发式/路径式加载的公开经验与失败样本（规则太长不被遵守、加载错规则等）。

**Q3 · 派生索引的漂移问题**：摘要/索引/登记表与原文脱节（stale index）的已知对策（生成时校验、CI 校验、访问时校验、定期重建）的实践。

**Q4 · 规则/规范文本场景的检索失败模式**：检索命中旧版规则、命中相似但不适用条款等问题的公开案例与对策（版本过滤、当前态过滤、权威性加权）。

**Q5 · 可嵌入本地 CLI agent 的检索工具现状**：无服务依赖、可本地运行的检索组件（如 ripgrep/BM25 库、SQLite FTS、sqlite-vec、tantivy、轻量 embedding 方案）成熟度、维护成本、与 agent 工作流的集成先例。

**Q6 · Token 预算下的选择策略**：加载预算内如何在"相关性 / 权威性 / 新鲜度 / 当前态"间加权取舍的公开方法；上下文污染率（装了没用的东西）如何测量与压低。

**Q7 · 结论清单**：基于证据回答——(a) 该量级下建议的最低成本方案与升级路径；(b) 每档方案的维护代价与失败面；(c) "人工分层加载表"在什么规模/复杂度之前仍是合理最优。
