Thought for 9m 26s

下面按你上传的研究定义来回答：这是一份现状可行性验证报告，不是完整实施方案，也不把未来能力当作当前依据。结论基于截至 2026-05-23 可查证的官方文档、真实产品、开源实践和研究资料。

1. 总体可行性结论

你的构想作为工程模式是现实可行的：把规则、状态、任务、交接、原始材料、评估报告等外部化到 Git / Markdown / 数据库 / RAG 存储中，让模型按需读取、生成更新、经人工或自动流程写回，这一模式已经在 coding agent、RAG、LangGraph、MemGPT / Letta 类系统、Cline Memory Bank、Claude Code、Codex、GitHub Copilot cloud agent 等方向得到不同程度验证。

但它不是在所有场景中都同等自动化。当前最强、最清晰、最可审计的是 本地/云端 coding agent 场景：Codex 可以在仓库内读取 AGENTS.md、编辑文件、运行检查、展示 diff、开 PR；Claude Code 可以读取 CLAUDE.md、维护本地 auto memory、使用 hooks/permissions 控制行为；GitHub Copilot cloud agent 可以在 GitHub Actions 环境中建分支、提交、开 PR。

普通 ChatGPT / Claude 纯对话场景则只能做到中等自动化：Projects、项目文件、记忆、聊天搜索、NotebookLM、Gemini notebooks、Study Mode、Khanmigo 等已经支持长期主题、学习、研究、资料库式对话；但“自动从 GitHub 拉取指定 memory 文件、对话结束自动写回仓库、自动生成 PR、长期可审计版本链”并不是普通聊天产品的默认能力。尤其是 ChatGPT 的 GitHub app 官方明确说它只能读取、分析和搜索仓库，不能 push code、updates 或 PR；OpenAI 文档把这类写回能力指向 Codex，而不是普通 ChatGPT GitHub app。

因此更准确的结论是：

“AI Agent 外部持久记忆系统”成立，但当前应被看作一种跨工具的工作流和治理架构，而不是一个普通聊天窗口里天然存在的功能。
它的核心价值不是让 AI “无所不记”，而是把长期 AI 工作拆成：可读规则、可检索记忆、可审计写回、可恢复交接、可迁移格式、可人工复核的版本链。

2. 非开发长期对话场景中，是否已有类似外部持久记忆实践？

有，但多数是局部实践，还没有像软件开发场景那样形成成熟、统一、版本化的外部记忆体系。

非开发场景里已经存在四类相关实践。

第一类是平台内置长期记忆与项目容器。ChatGPT Projects 官方定位为长期工作的 workspace，可把聊天、文件和自定义指令组织在一起；项目记忆可优先引用同一项目内的聊天和文件。Claude Projects 也提供项目知识库、项目指令和增强 RAG；Claude 还提供聊天搜索和记忆能力，可在新对话中搜索旧聊天并建立上下文连续性。

第二类是源材料驱动的个人知识库 / 研究助手。NotebookLM 是很典型的非开发长期话题实践：用户创建一个 notebook，上传 PDF、网站、YouTube、Google Docs、Markdown、PPT、CSV 等 sources，然后围绕这些 sources 对话、生成 study guide、briefing、mind map、quiz 等。它还强调回答基于 sources 并带引用。但 NotebookLM 的 sources 是导入时的静态副本，Google Drive 文件变更需要手动同步，其他 source 类型通常要手动删除后重新上传；这说明它更像“主题资料库 + 源材料问答”，不是自动写回的长期 agent memory。

第三类是AI tutor / AI coach / 学习模式。ChatGPT Study Mode 会用苏格拉底式提问、逐步解释、开放问题和反馈帮助学习，并且在 memory 开启时可根据过去聊天个性化学习指导。Khanmigo 是 Khan Academy 的 AI tutor / teaching assistant，明确主张不是直接给答案，而是引导学生思考；LearnLM 则是 Google 面向学习场景微调和研究的模型能力方向。这些都说明“长期学习进度、学习者画像、个性化指导”在非开发场景已经成为真实产品方向，但它们多数是平台内记忆和课程平台状态，不是用户自己可版本审计的外部 memory repo。

第四类是个人知识管理 + LLM / RAG / 外部笔记。LangGraph 文档把短期 memory 定义为 thread-scoped checkpoint，把长期 memory 定义为跨 session、按 namespace 存储的 user/application-level data；RAG 研究也证明把非参数化外部知识库接入模型是成熟方向。这个实践可以迁移到课程学习、语言学习、源码阅读、长期研究，但普通用户通常需要 NotebookLM、Obsidian、Git、脚本、RAG 工具或自建应用来实现，而不是直接靠聊天窗口。

所以，对你第 3 个新增问题的判断是：当前最系统地意识到“长期记忆、handoff、规则文件、项目状态、审计写回”的，确实主要是 coding agent / 开发者工具场景。 普通对话用户也有类似需求，但产品形态更偏 Projects、Memory、Notebook、AI tutor、personal knowledge base，而不是 Git 化的外部记忆体系。

3. 开发场景经验能否迁移到普通长期对话、教学、研究和源码学习？

可以迁移，而且很值得迁移；但不能原样照搬。

可以直接复用的是文件式状态管理思想：
AGENTS.md / CLAUDE.md 可以变成“对话行为规则”；project-state 可以变成“主题状态”；tasks 可以变成“学习任务 / 研究 backlog”；ADR 可以变成“长期结论与决策记录”；memory-ledger 可以变成“主题记忆账本”；handoff-current 可以变成“跨对话交接卡”；archive 可以变成“原始对话、资料和引用归档”。Cline Memory Bank 已经把这种做法以 Markdown 文件形式落地到开发场景：projectbrief.md、activeContext.md、systemPatterns.md、progress.md 等文件让 agent 在新 session 里重新建立项目理解。

需要改造的是验证机制。软件开发有 tests、lint、typecheck、diff、PR review；普通研究和学习没有天然的单元测试。因此非开发场景需要改成“证据引用、反例记录、概念掌握检查、学习回顾、来源可信度、未决问题列表、结论版本历史”。NotebookLM 的 source citation、ChatGPT Study Mode 的理解检查、Claude / ChatGPT Projects 的文件和项目指令，都可以作为迁移后的支撑点。

需要谨慎处理的是写回权限。开发工具可以直接改仓库文件，但普通长期对话中自动写回个人记忆很容易污染记忆、固化误解或泄露隐私。更现实的做法是让 AI 生成“记忆更新建议包”，用户确认后写入 Markdown / Git / Notebook / Obsidian。这个模式也符合 MCP 官方安全思路：工具调用和外部系统访问需要用户同意、权限边界和审计。

4. 六个关键链路逐项可行性分析
4.1 规则加载链路

结论：开发 agent 场景强可行；纯对话场景中等可行；规则过长会降低稳定性。

在开发场景，规则文件已经是成熟机制。Codex 文档支持全局 ~/.codex/AGENTS.md、仓库级 AGENTS.md、嵌套 AGENTS.md，并说明 Codex cloud 在运行时会使用仓库中的 AGENTS.md 来找到项目特定的 lint/test 命令。AGENTS.md 生态也已变成跨多个 coding agent 的开放格式，定位类似“给 agent 的 README”。

Claude Code 也有明确机制：每个 session 是 fresh context，但 CLAUDE.md 和 auto memory 会跨 session 承载知识；CLAUDE.md 会在 session 开始读取，可放项目约定、常用命令、架构说明等。Anthropic 同时警告，这些是 context，不是强制配置；越具体、越简洁越容易遵守，文档还提示过长的 CLAUDE.md 会降低 adherence，并建议控制在较短范围。

Cursor 也有 Project / Team / User Rules，并支持 AGENTS.md / .cursor/rules 类规则；不过 Cursor 官方页面在抓取时内容较少，最稳的证据来自 Cursor 搜索结果、AGENTS.md 生态和 Kilo Code 对 AGENTS.md 跨工具支持的说明。

纯对话场景可以用 ChatGPT Custom Instructions、ChatGPT Projects instructions、Claude Project instructions、NotebookLM / Gemini notebooks custom instructions 承担“行为规则文件”角色，但它们通常不是自动从 Git 仓库加载，也不天然进入 Git 版本审查链。ChatGPT Projects 和 Claude Projects 都支持项目级 instructions；Claude 文档明确说项目 instructions 会应用于项目内聊天，但项目内聊天的上下文不会自动跨聊天共享，除非加入项目知识库。

自动化边界：
开发 agent 可自动读取；纯对话通常需要用户上传、放入 Project、手动引用或通过 connector/RAG 引入。规则应短、分层、可审查，不能把完整历史和大量政策都塞进一个巨型规则文件。

4.2 记忆读取链路

结论：读取外部记忆是可行的，但读取方式差异很大；“按需加载相关记忆”比“全部塞入上下文”更现实。

ChatGPT 普通对话可以通过文件上传、Projects、memory、connectors、apps 读取外部信息。ChatGPT GitHub app 能连接仓库并基于代码、README、文档等 live data 推理，但官方同时说明它只能搜索 repository names，不能搜索 specific filenames；这对“新对话一句话读取某个指定 memory 文件”是重要限制。

Claude 普通服务也支持 Projects、项目知识库、RAG、聊天搜索和记忆。Claude Projects 可上传 docs/text/code，接近上下文限制时使用增强 RAG；Claude 的 chat search 可以跨旧聊天检索相关信息，项目内搜索则限定在具体 project。

本地开发 agent 读取仓库内 memory 文件最自然：Codex CLI 可以读取 repository、编辑文件、运行命令；Claude Code 会读取 CLAUDE.md，并可读取任意被授权工作区文件；Cline Memory Bank 直接把 memory 放在项目 Markdown 文件中。

云端 coding agent 读取也可行，但受授权和环境限制。Codex cloud 会 checkout repo，在容器中运行 setup 和 agent 命令；GitHub Copilot cloud agent 在 GitHub Actions ephemeral environment 中研究仓库、修改代码、运行测试。

RAG / LangGraph / MemGPT 支持更一般的“按需记忆读取”。LangGraph 明确区分短期 thread-scoped memory 和跨 session namespace 的 long-term memory，并支持 checkpoint、semantic search、memory store；MemGPT 研究则把 LLM 限制类比为操作系统内存管理，通过多层 memory 和 virtual context management 支持长对话和文档分析。

自动化边界：
普通聊天产品能读，但经常需要用户选择 Project、上传文件、选择 connector 或明确提示；开发 agent 能直接读 repo；真正的“智能相关记忆检索”通常需要 RAG、LangGraph、MCP、脚本或自建应用。

4.3 Handoff 生成与恢复链路

结论：handoff 在所有场景都可行；纯对话中最现实的是手动生成/复制；开发 agent 有 session resume、checkpoint、memory bank 等更强机制。

普通 ChatGPT / Claude 对话非常适合生成结构化 handoff：当前目标、已做结论、关键证据、未决问题、下一步、artifact refs。问题是自动恢复弱：新对话未必自动知道旧对话，除非在同一 Project、启用 memory、用聊天搜索、手动粘贴 handoff 或上传 handoff 文件。Claude 的聊天搜索和记忆能改善跨对话连续性，但这仍是平台内能力，不等于外部可审计 handoff。

Claude Code 有更明确的 session 机制：session 是与项目目录绑定的保存对话，可用 claude --continue、claude --resume、/resume 恢复，SDK sessions 还说明 session 包含 prompt、tool calls、tool results 和 responses；但 sessions persist conversation，不 persist filesystem，文件快照仍需 checkpointing。

Codex CLI 也支持 /compact 压缩早期 turns、/resume 恢复 saved conversation、/fork 克隆对话、/diff 查看 Git diff；这说明 coding agent 已经把“会话压缩、恢复、分叉、diff”产品化。

LangGraph 的 checkpoint 更接近工程级恢复：每一步保存 graph state，支持 human-in-the-loop、conversation memory、time travel、fault tolerance 和 replay/fork。它适合自建 agent，不是普通网页聊天默认能力。

Cline Memory Bank 提供了一个很贴近你构想的案例：上下文快满时先让 Cline “update memory bank”，再开新对话，让它 “follow your custom instructions” 读取 Markdown memory 继续工作。这个流程不是全自动，但非常现实。

自动化边界：
handoff 内容应引用 artifact refs，而不是复制全部历史；纯对话以手动交接卡最稳；开发 agent 可以用 session resume + 文件式 handoff + Git diff；自建 agent 可用 LangGraph checkpoint。

4.4 记忆写回链路

结论：这是当前最大分水岭。开发 agent 强可行；普通 ChatGPT/Claude 网页端弱可行或需额外工具；自动写回必须有人类确认和权限控制。

ChatGPT GitHub app 的边界非常明确：官方说它只能读取、搜索和分析，不能 push code、updates 或 pull requests；如果要生成、编辑、push、开 PR，OpenAI 指向 Codex。

ChatGPT Apps / Agent / Tasks 的情况更细。Apps 文档说部分 app 可以执行 write actions，是否能写取决于 app 和配置；OpenAI 也在 Business / Enterprise / Edu 中测试完整 MCP，包括 modify/write actions。但这并不等于普通 ChatGPT GitHub connector 当前能自动写回你的 GitHub memory repo。Tasks 还能定时执行，但官方特别说明：如果 task 是在带文件的 project 中创建的，task 不会访问那些 project files。

Claude 网页端 Projects 可以使用项目知识和 instructions，但官方资料并未证明普通 Claude 网页端能自动写回外部 Git 仓库。Claude Cowork 更接近非开发本地文件 agent：它可以在你电脑上读取/写入你选择的本地文件，并有项目文件、instructions、memory；但它是桌面本地任务，且文档说明 Cowork projects 目前 desktop-only、local-only、无云同步、不与 Claude Code 共享。

Claude Code、Codex、GitHub Copilot cloud agent 则可以写回。Codex app 支持本地/工作树/云模式、Git diff、stage/revert、commit、push、create PR；Codex cloud 能产生 diff 并可开 PR；Claude Code GitHub Actions 需要 repo contents/issues/PRs 的读写权限，可以修改 repo 文件、创建 PR、push changes；GitHub Copilot cloud agent 能创建分支、提交、推送并开 PR。

自动化边界：
纯对话中最稳做法是“AI 生成 memory update patch，用户确认后手动写入”；本地 agent 可直接修改 memory files，但建议用 Git diff / patch / commit review；云端 agent 写回最好走 PR。自动无审查写回长期记忆不建议。

4.5 版本审计链路

结论：Git 非常适合外部记忆审计；这一链路现实依据最强。

Git / GitHub 天然支持版本、diff、branch、回滚、PR、review。GitHub Actions 是 CI/CD 和事件自动化平台，可在 PR、issue 等事件触发 workflows；CODEOWNERS 可以为特定路径指定 reviewer；protected branches 可以要求 code owner review；required reviews 可要求 PR 在合并前获得指定数量审批。

这意味着 memory files、handoff、topic cards、learning profile、project-state、ADR、evaluation reports 都可以像代码一样被审查。对于开发项目，规则文件和记忆文件可以和代码同仓，方便 agent 读取；对于非开发项目，Git / Markdown / Obsidian / NotebookLM / Google Docs 可以承担不同层级的审计，但 Git 的版本审计最强，NotebookLM 的优势是 source-grounded 对话和学习 artifacts，而不是 Git 式审计。

自动化边界：
Git 能审计“文件变更”，不能自动保证记忆质量；仍需要人工 review、来源引用、反事实检查、敏感信息扫描和定期整理。

4.6 跨环境迁移链路

结论：Markdown / Git / artifact refs / RAG index 是相对模型无关的；平台内 memory 和规则语法需要 adapters。

模型无关的部分包括：原始资料、对话归档、topic cards、handoff、decision log、task log、evaluation report、artifact refs、source index。只要用 Markdown / JSON / YAML / Git 保存，ChatGPT、Claude、Codex、Claude Code、Cursor、NotebookLM、本地脚本都能不同程度读取。

需要适配的部分包括：ChatGPT Project instructions、Claude Project instructions、AGENTS.md、CLAUDE.md、Cursor Rules、MCP server config、GitHub Actions workflow、Claude Code hooks、Codex config。Claude Code 明确只读取 CLAUDE.md 而不是 AGENTS.md，但可以让 CLAUDE.md import AGENTS.md；Codex 使用 AGENTS.md；AGENTS.md 生态声称可跨多种 coding agent，但每个工具的加载顺序、优先级和权限不同。

Claude 还提供 memory import/export 实验能力，可把 Claude 看到的 memory 导出或导入，但文档也提示这是 experimental，未必总能正确纳入。ChatGPT memory 也可管理和搜索，但仍是平台内记忆，不等于外部、版本化、跨工具自动同步。

自动化边界：
应设置 adapters/ 或等价层保存平台差异。跨环境迁移的核心不是复制每个平台的 memory，而是保持一个外部 source of truth，再为各工具生成短规则、短状态和当前 handoff。

5. 四类运行场景分析
场景 A：纯对话和非开发长期话题

可行性：中等。读取和组织可行，写回和审计弱。

适合场景包括长期课程学习、英语学习、Linux 内核/数据库/编译器源码学习、长期研究、个人知识训练、方案打磨。ChatGPT Projects、Claude Projects、NotebookLM、Gemini notebooks、Study Mode、Khanmigo 都说明非开发长期主题记忆已经是现实需求。

普通用户可以维护一个 GitHub 私有仓库或本地 Markdown 文件夹作为“主题记忆库”，但在 ChatGPT / Claude 网页端通常需要手动上传、放入 Project、使用 connector、或粘贴 handoff。ChatGPT GitHub app 读仓库可以辅助，但不能写回，也不能按官方文档保证按 filename 检索指定文件。

最现实工作流是：
每个长期主题有一个 topic-card.md、learning-profile.md、decision-log.md、handoff-current.md、archive-index.md；每次对话结束让 AI 生成“本轮记忆更新建议”，用户检查后写入。自动化可通过脚本、GitHub Actions、MCP app、API 或本地 agent 增强，但不应假设普通网页聊天能全自动完成。

场景 B：本地开发 Agent

可行性：高。最适合当前构想。

Codex CLI / app、Claude Code、Cursor、Cline、OpenHands 这类本地 agent 能读取本地 repo、修改文件、运行测试、生成 diff。Claude Code 还有 CLAUDE.md、auto memory、hooks、permissions、sessions；Codex 有 AGENTS.md、worktree、diff、commit、push、PR；Cline Memory Bank 用项目 Markdown 文件维护跨 session 上下文。

长期记忆文件应放进 Git，但要避免 agent 误改。可以把规则文件设为需要用户确认修改，或者用 hooks 阻止直接改某些路径；Claude Code hooks 可在 lifecycle points 自动格式化、阻止 protected files、注入 context、审计配置变化。Kilo Code 文档也说明 AGENTS.md / AGENT.md 可被写保护，AI 修改时需要用户确认，这种模式很适合 memory governance。

本地 agent 的优势是：能直接访问文件系统、能运行验证命令、能生成 patch、能由用户实时批准或拒绝，隐私暴露也比云端可控。

场景 C：云端 Coding Agent

可行性：高，但必须用权限和 PR 控制。

Codex cloud、GitHub Copilot cloud agent、Claude Code GitHub Actions 都已经支持云端环境中读取仓库、修改文件、运行检查、开 PR 或推送分支。Codex cloud 创建容器并 checkout repo；GitHub Copilot cloud agent 在 GitHub Actions 环境中研究代码、修改、运行测试；Claude Code GitHub Actions 可在 PR/issue 中通过 @claude 工作，且需要 repo 内容、issues、PRs 的读写权限。

记忆与代码同仓通常最可行：agent 只需访问一个 repo，记忆文件与代码变更一起审计。独立 memory repo 也可以，但需要额外授权、跨 repo checkout、访问 token、权限隔离；敏感记忆不应暴露给云端 agent，尤其是个人隐私、API secrets、内部策略、客户数据。Codex cloud 文档说明 secrets 只给 setup scripts，出于安全原因在 agent phase 前移除，这说明云端 agent 的安全边界必须认真设计。

写回最好必须走 PR。PR 可保留 diff、评论、review、Actions 检查、CODEOWNERS 审批和回滚路径。

场景 D：多 Agent / AI 团队

可行性：中高，但工程复杂度显著上升。

多 agent 已有真实框架和产品实践。CrewAI 支持 agents、crews、flows，并有 memory；文档说明开启 memory 后，crew 会在每个 task 后抽取离散 facts 存储，在每个 task 前召回相关 context，且可区分 shared memory 和 agent scoped memory。LangChain / LangGraph 有 subagents、handoffs、skills、router 等多 agent 模式；Claude Code 有 subagents，子 agent transcripts 可单独保存；GitHub Copilot cloud agent 也开始支持 custom specialized agents。

多 agent 适合共享外部记忆，但必须加 namespace 和写入协议。否则会出现写入冲突、重复总结、错误记忆互相污染。比较稳的模式是：manager agent 负责任务分解和最终写回；implementation/test/review agents 只写临时 notes；memory maintainer agent 生成 memory patch；人或 CODEOWNERS 审核后合并。

多 agent 经验可以反哺普通长期对话：普通学习/研究也可以分“导师 agent、资料整理 agent、反驳 agent、记忆维护 agent”，但若没有外部文件和审核机制，多 agent 只会增加复杂度和幻觉传播风险。

7. 已有强现实依据的机制

最强现实依据包括：

文件式规则：AGENTS.md、CLAUDE.md、Cursor Rules、Project instructions 已经是现实产品机制。

外部记忆读取：Projects、files、GitHub connector、repo files、NotebookLM sources、RAG、LangGraph memory store 都支持读取外部知识。

handoff / checkpoint / resume：Claude Code sessions、Codex /resume / /compact / /fork、LangGraph checkpoints、Cline Memory Bank 都支持不同层级的恢复。

Git 审计写回：Codex、Claude Code GitHub Actions、GitHub Copilot cloud agent、GitHub PR / Actions / CODEOWNERS / protected branches 共同证明“记忆像代码一样审查”是可行的。

非开发长期话题容器：ChatGPT Projects、Claude Projects、NotebookLM、Gemini notebooks、Study Mode、Khanmigo 证明非开发长期主题、学习进度、资料库对话是真实需求。

8. 只能半自动实现的机制

纯对话中的跨会话 handoff，目前最可靠仍是让 AI 生成交接卡，然后用户复制到新对话或外部文件。

普通 ChatGPT / Claude 对话中的记忆写回，通常应由 AI 生成“建议更新”，用户手动确认后写入 Git / Markdown / Obsidian / NotebookLM。

ChatGPT GitHub connector 读取指定 memory 文件不应假定完全稳定，因为官方说不支持按 specific filenames 搜索。

NotebookLM / Gemini notebooks 可形成长期知识库，但 sources 变更同步和跨 notebook 访问有限，需要人工维护。

Claude / ChatGPT 平台内 memory 可帮助连续性，但不等于完整历史归档，也不等于可审计版本记忆。ChatGPT memory 文档说明它不会记住每个细节；Claude memory summary 也有更新周期和可编辑/导出边界。

9. 需要 API、脚本、MCP、GitHub Actions 或自建工具的机制

需要额外工具的包括：

自动从普通聊天抽取 memory delta、去重、分类、打标签、写入 GitHub PR。

跨 ChatGPT / Claude / Codex / Claude Code / Cursor 的统一 memory index 和 adapters。

对 memory updates 运行质量检查，例如敏感信息扫描、引用完整性检查、重复记忆合并、过期记忆标记。

把 NotebookLM / Obsidian / GitHub / 本地 Markdown / 数据库同步成统一 RAG index。

让 ChatGPT 通过自定义 MCP app 对外部 memory repo 执行受控写入；OpenAI 文档支持 MCP remote servers 和部分 write actions，但实际是否可写取决于计划、app、管理员配置和工具权限。

云端 agent 任务失败后自动生成 checkpoint、handoff 和 artifact refs，也通常要通过 GitHub Actions workflow、agent hooks 或自建脚本完成。GitHub Actions 本身适合事件触发自动化，但具体 memory workflow 需要你定义。

10. 目前不现实或不建议做的机制

不建议把所有长期记忆都塞进一个超长 prompt。研究显示长上下文模型对中间信息利用并不稳，存在 “lost in the middle” 问题；LangGraph 文档也明确说长对话会让模型分心、变慢、成本变高，即使上下文窗口够大也会性能下降。

不建议让 AI 无审查自动改长期记忆。长期记忆一旦污染，会在后续对话中反复放大错误。

不建议把敏感个人记忆、密钥、内部策略、客户数据暴露给云端 agent。云端 agent 需要最小权限、隔离、日志和 PR 审核。

不建议把平台内 proprietary memory 当唯一 source of truth。它有帮助，但不够可审计、可迁移、可回滚。

不建议用巨型 AGENTS.md / CLAUDE.md 管一切。官方和实践都倾向于短、具体、分层、按需加载。

13. 后续让普通 ChatGPT、Codex 或 Claude Code 起草方案时的参考要点

后续具体方案应把“外部记忆”分成至少三层：规则层、状态层、证据层。规则层短而稳定；状态层记录当前主题、任务、结论、handoff；证据层保存原文、引用、artifact refs、评估报告。不要把证据层全部加载进 prompt，而是用索引/RAG/文件引用按需取用。

对普通长期对话，优先设计“半自动安全流程”：
AI 读取 handoff-current 和 topic-card，开始工作；结束时生成 memory-update-proposal；用户确认后写入。这样比追求网页端全自动写回更现实。

对开发 agent，优先用 Git：
所有长期记忆修改走 diff；高风险路径走 CODEOWNERS；云端 agent 走 PR；本地 agent 可直接改，但 commit 前人工 review。记忆文件和代码文件一样需要测试、lint、敏感信息扫描和回滚策略。

对跨工具迁移，设置一个模型无关的 source of truth，再生成 adapters：
AGENTS.md 给 Codex / Cursor 等；CLAUDE.md 给 Claude Code；ChatGPT/Claude Projects 使用短版 project instructions；NotebookLM 使用 sources + custom instructions；MCP/GitHub Actions 负责自动化桥接。

对非开发场景，采用“开发概念的语义替换”：
ADR → 长期结论记录；task backlog → 学习/研究任务；project state → topic state；handoff → 跨对话交接卡；test report → 自测/理解检查/证据复核报告；artifact refs → 原文、笔记、图表、代码片段、课程材料引用。

14. 课外阅读方向，但不作为当前可行性依据

值得继续关注但不应作为当前方案可行性依据的方向包括：更强的 agent memory、long context 可靠性改进、MCP write actions 普及、Claude Cowork / Codex / ChatGPT Apps 的未来写回能力、LearnLM / AI tutor 的长期学习画像、LangGraph / CrewAI / OpenHands 等框架的生产化、多 agent 记忆 namespace 和冲突解决。

当前真正可靠的落点仍然是：外部文件 + 短规则 + 按需检索 + handoff + 人工确认写回 + Git 审计。这套组合现在就能在开发场景高度自动化，在普通长期对话场景半自动落地，并且具有跨 ChatGPT、Claude、Codex、Claude Code、Cursor、NotebookLM 和自建 RAG/MCP 工具迁移的现实基础。
