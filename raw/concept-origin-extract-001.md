## 1. 背景：从研究假设转入正式设计

### 用户近原文

本对话长期讨论的是：面向长期 AI 工作的外部持久记忆系统。

它最初来自用户对以下问题的思考：

- 跨对话记忆断裂；
- 长期学习和长期研究中进度丢失；
- AI 自动化开发中上下文无法稳定继承；
- 源码学习、多 Agent 协作和复杂项目中的记忆断裂；
- ChatGPT / Claude 等平台内部 memory 不够可见、可编辑、可迁移、可审计。

早期讨论中曾经提出过一些目录结构、policy、schema、arch 分层、handoff 机制等草案。  
但用户后来明确修正：这些都是在深度研究验证之前假想出来的，不作为正式设计框架。后续应在研究结果基础上重新设计正式版本。

### 理由和考量

用户不希望把“先前凭直觉想出来的结构”直接固化为正式架构。  
原因是该系统要长期服务多个 AI 工具和多个项目类型，如果一开始的假设与真实工具能力不匹配，后续会积累大量错误抽象。

用户希望先通过研究报告确认：

- 普通 ChatGPT / Claude 纯对话到底能自动化到什么程度；
- Codex、Claude Code、Cursor、本地 Agent 和云端 Coding Agent 能做什么；
- GitHub / Git / Actions / PR / CODEOWNERS 对长期记忆系统有什么现实价值；
- 非开发长期对话和学习场景是否已经有真实实践；
- 开发场景的经验能否迁移到普通长期对话和学习场景。

### 助手核心回应

正式设计应从研究结论和能力边界出发，而不是继承旧草案。

后续流程应为：

1. 吸收研究结论；
2. 提炼可行能力边界；
3. 判断哪些机制可用、哪些只能半自动、哪些暂不做；
4. 再确定 MVP 架构、目录结构、规则文件、模板和部署流程。

## 2. 研究报告形成的总体边界

### 用户近原文

用户提供了 6 份 ChatGPT Plus 轻量版 Deep Research 子课题研究结果，以及 1 份 GPT Pro 版综合 Deep Research 结果。

用户要求：后续正式设计持久记忆系统时，必须严格依据各种 AI 模型、服务、配套工具或其他工具的能力和用法，绝对尊重研究报告结论，多参考研究报告中的案例。

如果某些部分不能确定是否符合现实和事实，或不能保证可行性，就需要将这些不确定内容单独列出并明确说明。

### 理由和考量

用户担心在这种系统设计中，模型容易把“理论上可能”说成“当前可用”，尤其是：

- 把普通 ChatGPT / Claude 对话窗口说成能自动读写外部仓库；
- 把 ChatGPT GitHub connector 误认为能 push / commit / PR；
- 把平台内部 memory 当成长期真相源；
- 把未来 MCP、Apps、Agent、Cloud capability 当作已经可用；
- 为了显得完整而设计出暂时无法落地的全自动系统。

因此用户要求不确定项必须单独放置，而不是混入正式方案。

### 助手核心回应

后续设计应使用证据等级：

- A 级：研究报告明确支持，且有真实工具、官方能力或成熟案例支撑；
- B 级：方向被研究报告支持，但具体实现受工具能力限制；
- C 级：工程上可能可做，但需要脚本、API、MCP、GitHub Actions 或自建工具；
- D 级：不确定，必须单列；
- E 级：研究报告明确不支持或不建议，不能作为当前方案基础。

关键边界：

- 不把普通 ChatGPT / Claude 对话窗口说成能自动读写外部记忆仓库；
- 不把 ChatGPT GitHub connector 说成能 push / commit / PR；
- 不把平台内部 memory 当作唯一真相源；
- 第一阶段不默认全自动写回；
- 不把未来产品能力当成当前可用能力；
- 旧草案不得作为默认框架。

## 3. 研究报告的整体结论

### 用户近原文

用户希望先对研究结论有整体简要了解，而不是立即进入目录结构或模板设计。

### 助手核心回应

研究报告整体支持核心判断：

> “AI Agent 外部持久记忆系统”不是幻想，而是已有现实依据的工程模式；但当前最可靠的落地形态不是全自动记忆，而是“外部文件 / Git / Markdown 作为真相源，AI 生成更新建议，人类确认，必要时由本地或云端 Agent 写回并审计”。

主要结论：

1. 这个系统不是单一产品功能，而是跨工具工作流和治理架构；
2. 开发 Agent / Coding Agent 场景最成熟；
3. 普通 ChatGPT / Claude 纯对话窗口最薄弱，主要适合半自动；
4. 非开发长期对话已有实践，但不够系统化；
5. 开发场景经验可以迁移，但要语义改造；
6. 长上下文不能替代外部记忆；
7. handoff、checkpoint、rolling buffer 合理；
8. Git 是当前最强的审计层；
9. 第一阶段应做半自动、安全、可审查的外部记忆系统。

### 理由和考量

这个结论对用户构想很关键，因为用户的目标不是证明“长期记忆有用”，而是要判断如何落地。  
研究报告提供了一个现实边界：

- 本地 / 云端 Coding Agent + GitHub 可以实现较强写回和审计；
- 普通对话窗口更多依赖复制、上传、Projects、handoff 和人工确认；
- Git / Markdown 能提供跨模型、跨工具、跨时间的真相源；
- RAG、checkpoint、handoff 支持按需加载，而不是全部塞进上下文。

因此后续设计应避免“普通聊天窗口里全自动长期记忆”的幻想，转向“外部仓库 + 半自动流程 + 可审计写回”。

## 4. Git / GitHub 与自动化记忆程度

### 用户近原文

用户注意到：AI Agent 开发场景自动化记忆程度较高，并显式涉及 Git。  
用户询问这是否因为 Git / GitHub 有很多利于自动化存储的功能。  
如果所有使用场景都使用 GitHub 或类似工具存储，是否也能提升各场景下自动化记忆程度？GitHub 的自动触发、动作、工作流等功能能提供哪些便利？

### 理由和考量

用户的真实关注点不是“GitHub 是否流行”，而是：

- 是否可以把 GitHub 当成所有长期记忆系统的统一底座；
- 是否可以让非开发场景也享受开发场景的版本化、diff、审计和自动化；
- 是否可以用 GitHub Actions 等能力减少手工维护成本；
- 是否能让未来不同 Agent 或模型共享同一个可追溯外部状态。

### 助手核心回应

Git / GitHub 对持久记忆系统确实有天然优势：

- 把记忆变成普通文件；
- 提供版本链；
- 提供 diff、commit、branch、PR、review、rollback；
- 支持 GitHub Actions 事件触发；
- 支持 CODEOWNERS 和分支保护；
- 可作为外部状态机、审计系统和自动化执行平台。

但边界是：

- GitHub 提升的是外部记忆管理层，不一定提升普通聊天窗口本身的自动写回能力；
- 普通 ChatGPT / Claude 对话仍不能默认自动写 GitHub；
- 自动化需要 Codex、Claude Code、GitHub Actions、MCP、脚本或用户手动操作；
- 敏感内容不能随便交给云端 Agent；
- 非开发场景第一阶段不必上完整 PR / CI / CODEOWNERS 流程。

建议分级：

- Level 0：本地 Markdown；
- Level 1：本地 Git；
- Level 2：GitHub 私有仓库；
- Level 3：PR / review / branch protection；
- Level 4：Actions 自动检查、索引、归档；
- Level 5：Codex / Claude Code / cloud agent 生成 PR；
- Level 6：MCP / API / 自建服务实现受控写回。

## 5. 是否需要“记忆系统元 Agent”

### 用户近原文

用户提出：是否有必要建立一个 AI Agent，它的工作就是专门为各种项目 / 场景的需要来定制记忆系统？

### 理由和考量

用户逐渐意识到，不同场景的记忆结构差异很大：

- 软件开发项目需要 project-state、tasks、ADR、tests、code review、CI 记录；
- 语言学习需要学习者画像、课程进度、错题、词汇掌握、复犯率；
- 源码学习需要版本、子系统、关键文件、调用链、结构体、未解问题；
- 长期研究需要假设、证据、结论、反例、资料索引、开放问题；
- 普通长期对话需要 topic-state、handoff、decision-log 和隐私边界。

如果每次都由用户手动设计这些 schema，成本很高，也容易不完整。  
因此需要一个上层工具专门回答：

- 这个场景需要记住什么；
- 什么是长期记忆；
- 什么只是短期 buffer；
- 哪些必须人工确认；
- 哪些可以 Agent 更新；
- 哪些应该进 Git；
- 哪些不能进云端；
- 不同工具如何适配。

### 助手核心回应

有必要建立“Memory System Architect Agent”：

> 一个根据场景、工具能力、隐私要求和自动化边界，生成并维护外部持久记忆系统的元 Agent。

它不是普通记忆库，而是设计和交付记忆系统的上层工作空间。  
第一阶段不应是无监督自动记忆管理员，而应是：

- 设计者；
- 生成器；
- 审查者；
- 维护建议者。

职责包括：

- 场景识别；
- 能力边界判断；
- 设计 memory schema；
- 设计 handoff；
- 设计 buffer / archive；
- 设计平台适配文件；
- 设计写回和审核流程；
- 定期审查记忆系统本身。

## 6. 持续演进型元 Agent

### 用户近原文

用户补充：自己不是 AI Agent 项目架构专家，无法一开始就为特定用途的 AI Agent 或 agent 团队设计好完善架构。  
记忆系统也一样，无法一开始考虑完善。

因此，“记忆系统元 Agent”要能在用户断断续续提出新需求、反馈现有设计使用体验时，持续改进和完善设计。

还要考虑多种需求来源：

- 用户直接提出需求；
- 其他 AI Agent 或元 Agent 整理出持久记忆相关需求后转交给 Mnemosyne。

同时还要考虑 Mnemosyne 自举自己的记忆系统。  
还要考虑为多个需求设计的记忆系统设计书保存在哪里：是放在对应目标项目中，还是保存在 Mnemosyne 自己仓库中，再交付到目标项目。

### 理由和考量

用户的核心担忧是：

- 自己不可能一次性设计出完备系统；
- 长期项目会不断出现新反馈和新需求；
- 目标项目可能很多，每个项目需求不同；
- 如果设计过程散落在各项目中，Mnemosyne 无法积累跨项目经验；
- 如果所有设计只放在 Mnemosyne 中，目标项目运行时又可能与设计原本脱节；
- 因此需要同时保留“设计工厂”和“运行真相源”的概念。

### 助手核心回应

Mnemosyne 应被设计为持续演进型设计 Agent，而非一次性模板生成器。

推荐双层模式：

- Mnemosyne 仓库：设计工厂 / 设计档案 / 模板库 / 跨项目经验库；
- 目标项目仓库：具体项目实际运行的记忆系统文件。

主副本规则：

- 设计孵化期：Mnemosyne 仓库是主副本；
- 项目部署后：目标项目仓库成为运行真相源；
- Mnemosyne 保留设计档案、交付记录和后续改进建议；
- 后续改动通过 change proposal / release package / delivery manifest 同步。

Mnemosyne 自己也必须有记忆系统，用来记录：

- 自身职责；
- 设计原则；
- 工具能力边界；
- 已管理项目清单；
- 需求 inbox；
- change request；
- 设计决策；
- 不确定项；
- 模板库；
- 跨项目经验总结。

## 7. 原文保存、派生整理与执行源

### 用户近原文

用户强调：对需求描述和使用体验反馈需要保留原文。

原因有两点：

1. 避免由某个模型分析加工过的版本，在更换模型后产生误差。  
   这里不仅包括更换另一家模型，也包括同一家同一系列模型推出新版本。

2. 长期使用和维护同一个自动开发项目时，用户过一段时间可能忘记早期需求的考量和想法，需要不断回顾、修正和补充。

同时用户指出：原文总量会很长，不适合各模型每次完整读取。  
应该让各模型通过原文形成自己用的整理版、精简版、索引版，以减少读取成本。

随后用户又修正：原文最忠实，但人类思考会变化。同一个问题不同时期可能有不同想法，新版本不一定比旧版本更好。  
因此还需要一层给人看的整理版，即用户决定实施到项目中的版本。

### 理由和考量

用户把“保留原文”和“当前执行”区分开，是因为发现仅仅说“原文是最高真相源”也有问题：

- 原文可能包含阶段性想法；
- 原文可能重复；
- 原文可能相互冲突；
- 后来的想法不一定更成熟；
- 用户本人未来也可能忘记当时理由；
- 模型如果直接把“用户曾经说过”当作“用户现在决定实施”，会导致错误执行。

因此需要三种“真相”：

- 历史真相：raw 记录；
- 分析真相：candidate / normalized requirement；
- 执行真相：human-approved-spec。

### 助手核心回应

正式分层应为：

1. Idea Capture Buffer：速记点子池，保存非常粗糙的临时想法；
2. Raw Archive：原文证据层；
3. Candidate Ideas / Candidate Requirements：候选想法层；
4. Similarity / Conflict Index：查重与冲突层；
5. Human-Approved Spec：人类确认实施版；
6. Active Context：当前工作上下文。

核心原则：

- 原文是证据，不是执行源；
- 模型摘要是派生视图，不是执行源；
- 候选需求不是执行源；
- Human-Approved Spec 是项目当前执行源。

Human-Approved Spec 的作用，是防止系统把“用户曾经说过”误当成“用户现在决定实施”。

## 8. 新需求查重与差异报告

### 用户近原文

用户指出：某方面需求和想法提出后，相隔一段时间又会因各种原因再提出一遍，而且新版本和旧版本可能有差异，新想法不一定比旧版更好。

因此 Mnemosyne 需要一种能力：当新想法提出后，查重找出相同或相似旧版本，主动向用户说明它们的差异和具体实施时的不同，然后让用户决定实施版如何书写。

### 理由和考量

用户担心：

- 自己可能反复提出相似需求；
- 表述略有不同；
- 新说法可能只是临时想法；
- 旧说法可能上下文更完整；
- 如果模型只看最新输入，可能覆盖早期更成熟版本；
- 如果全部保留，又会让需求越来越乱。

因此需要“新旧需求 reconciliation”流程，而不是“最新输入自动胜出”。

### 助手核心回应

Mnemosyne 需要 Requirement Similarity & Reconciliation 能力。

新需求流程：

1. 保存原文；
2. 生成 candidate；
3. 查找相似旧需求；
4. 生成 Similarity Report；
5. 说明相同点、不同点、冲突和可能合并方式；
6. 给出选项：
   - merge；
   - replace；
   - keep_parallel；
   - defer；
   - reject；
   - keep_candidate；
   - ask_followup；
7. 用户确认后才更新 Human-Approved Spec。

常见关系：

- duplicate；
- similar；
- refines；
- supersedes；
- contradicts；
- depends_on；
- derived_from；
- rejected_by；
- merged_into。

## 9. Idea Capture Buffer / 临时点子速记池

### 用户近原文

用户提出一个小功能：突然跳出来的想法需要速记和单独存储。

原因是用户记忆力不太好，经常有点子想出来很快忘记，或者一次想出很多点子，但深入其中一个时忘记另一些。  
这些点子通常很粗糙，不适合直接加入原文，更无法直接加工后作为方案内容实施。  
这个功能还需要外部设备和工具协作，所以暂时作为 TODO，后续建立 Mnemosyne 后再详细设计。

### 理由和考量

用户区分了三类内容：

- 正式需求：已经足够明确，可以进入 raw / candidate 流程；
- 使用反馈：来自真实体验，应保存原文并分析；
- 临时点子：非常粗糙、易丢失，但不能污染正式需求系统。

Idea Capture Buffer 的价值是低摩擦捕获，不是立即进入正式设计。

### 助手核心回应

Idea Capture Buffer 应作为第 0 层：

- 不等于原始正式需求；
- 不等于候选需求；
- 不等于 Human-Approved Spec；
- 是更早一层的 idea inbox / capture buffer。

流程：

1. 快速捕获；
2. 暂存；
3. 定期整理；
4. 查重；
5. 标记为可转候选、暂存、重复、无效或待补充；
6. 用户确认后再进入正式需求流程。

当前只作为 TODO，不进入 v0.1 实现。

## 10. 冯诺伊曼式外部记忆架构

### 用户近原文

用户提出：模仿冯诺伊曼计算机硬件结构，将 AI 模型只作为运算器 / 中央处理器，将其他所有内容作为存储数据。

进一步类比：

- prompt、rules 等对模型工作内容和行为约束的存储，类似 CPU 指令或程序的 text 段；
- 模型要读取、分析和生成的内容，类似 data 段；
- 模型内部记忆能力只当作内存或高速缓存；
- 通过外部文件和 handoff 保证模型新老对话正确、流畅、简便地交接工作。

### 理由和考量

用户提出该类比的目的，是把模型从长期状态源中剥离出来：

- 模型可以升级或替换；
- 对话可以重启；
- 工作可以交接；
- 长期状态仍保存在外部可见、可审计、可迁移的位置；
- 指令和数据分离，避免规则文件被历史内容污染；
- 内部 memory 只能作为 cache，不能作为长期真相源。

这个类比帮助确定系统基本边界：模型负责计算，外部仓库负责记忆。

### 助手核心回应

该类比可作为正式设计的核心工程抽象，但不能当作模型内部机制的真实硬件描述。

建议表述：

> 模型计算无状态化，长期状态外部化，规则程序化，工作交接快照化，证据材料文件化，检索加载按需化。

成立的映射：

- CPU / 运算器：AI 模型；
- text 段：prompt、rules、policy、workflow；
- data 段：需求、任务、原文、项目状态、学习记录、源码笔记；
- RAM / 工作内存：当前对话上下文、active-context；
- cache：模型内部 memory、项目记忆、摘要；
- 硬盘：Git / Markdown / 数据库 / RAG store；
- checkpoint：handoff-current、session summary；
- 文件系统索引：topic-index、source-index、requirement-index。

边界：

- 模型不是确定性 CPU；
- prompt 不是机器码；
- 模型内部状态不可完全观察；
- 关键状态必须外部化、可审计、可回滚。

## 11. 模型迁移与约束生命周期

### 用户近原文

用户提出问题：如果一个项目使用 GPT-5.5 工作一段时间，OpenAI 发布 GPT-6 后决定迁移，应该让新模型从原文重新整理加工版，还是从旧模型加工版继承？

用户不确定重新分析会消耗多少算力。  
同时，为旧模型稳定可靠工作而设置的一些行为约束，在新模型中可能变成废话；新模型新增能力也需要利用。

### 理由和考量

用户关注的是长期系统的“模型可替换性”。

如果完全继承旧模型加工版：

- 旧模型误解会延续；
- 旧模型能力不足导致的行为补丁会变成负担；
- 旧模型摘要中的偏差会长期固化。

如果完全重读全部原文：

- 成本可能很高；
- 可能耗时；
- 新模型也可能引入新解释偏差；
- 不一定比旧版本更符合用户意图。

因此需要折中机制。

### 助手核心回应

迁移策略不应二选一，而应：

> 旧加工版作为迁移基线，原文作为最高证据源，新模型按风险和价值选择性重分析。

分三层：

1. Raw Evidence：原文证据层；
2. Canonical Memory：模型无关正式记忆层；
3. Model-Specific Digest：模型专用加工层。

默认迁移：

- 继承 canonical memory；
- 读取 handoff 和 active-context；
- 读取 open questions 和 TODO；
- 对高风险、高价值、低置信度、用户多次纠正过的内容回查 raw；
- 复审旧模型专用约束；
- 验证新模型能力后再启用。

重分析等级：

- Level 0：不重分析；
- Level 1：索引级复核；
- Level 2：关键原文回查；
- Level 3：全量重分析。

默认 Level 1 + 局部 Level 2。

约束生命周期状态：

- active；
- deprecated；
- replaced；
- model_specific；
- review_on_model_upgrade；
- experimental；
- rejected。

## 12. 语言策略

### 用户近原文

用户一开始考虑过：用户内容保持原语言，模型生成内容英文为主，中文作为注释。  
后来用户重新考虑后决定：最好全部采用中文，除了文件名、路径名、命令等天然适合英文的内容。

原因：

- 用户当前主要使用中文交流；
- 多次读写 + 翻译可能产生歧义；
- 双语内容会增加空间占用；
- 未来当用户能流畅英文交流，或认真考虑好双语细节后，再转为英文或双语。

### 理由和考量

用户的核心考量是长期回顾和语义稳定。

Mnemosyne 是一个长期使用的私有设计仓库。  
如果正文使用英文或双语，用户未来回顾早期需求、理由和修正时，会增加认知负担。  
同时，模型翻译可能改变细微含义，而这些细微含义恰恰可能影响后续需求设计。

因此当前阶段采用中文正文更适合真实使用。

### 助手核心回应

当前语言策略：

- 仓库正文使用中文；
- 用户原文保持原语言，当前主要是中文；
- 模型整理后的用户需求仍用中文；
- 模型生成的设计说明也用中文；
- 不附带英文注释；
- 文件名、目录名、ID、状态值、YAML key、命令、Git/GitHub 术语、工具和产品名可以保留英文。

如果未来切换为英文或双语，应通过专门语言迁移流程处理。
