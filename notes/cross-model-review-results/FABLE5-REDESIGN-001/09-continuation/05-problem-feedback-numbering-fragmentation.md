## 5. 根因分析（供专项研究的起点，非结论）

1. **无盘点的正式化**：注册表把"从 001 开始"当成建表默认，没有"存量盘点→回填→再分配"的迁移义务——形式化一个已在使用的命名体系时未继承其历史；
2. **命名真相寄存在仓库之外**：1~13 序列只活在 ChatGPT 侧栏标题里，仓库无登记处，注册表建立时"看不见"它们（档案 8/28 才入 Alaya）；
3. **分配预检单源**：guard 已有"不得仅凭 UI 缺项推断空号"条款，但反向（不得仅凭注册表推断空号）无人执行；先兆事故（MNE-DR-003 撞号）未升级为分配规程；
4. **标识符焊死**：显示号被写进 canonical 任务 ID、文件/目录名、哈希收据（如 WORK-ULTRA-FABLE-MNE-DR-005-…），使事后纠偏只能绕行不能改判；
5. **多套词汇并行无对照**：UI 序列 / 文件标签 / 注册表三套各自演化，缺一张强制维护的对照表。

## 7. 未来专项研究的候选问题（Owner 立项时取用）

1. 命名/编号体系"正式化"时的**存量盘点与回填义务**如何成为通用规范（任何登记表建立=先盘点后分配）；
2. **分配前双源核对**（登记表＋档案/UI 实物 grep）可否脚本化为 preflight（同 scripts/preflight-write.sh 的机械化思路）；
3. 显示号进入 canonical ID/文件名/收据的**焊死代价**：是禁止混入，还是接受混入但声明永不改判？
4. "曾用号（former_number）"读档规则的通用化；
5. 先兆事故（首次撞号）→ 分配规程升级的触发线为何未动作（与反模式清单 #4"事故→规则无局部性判断门"的反向情形：这里是该升级而未升级）；
