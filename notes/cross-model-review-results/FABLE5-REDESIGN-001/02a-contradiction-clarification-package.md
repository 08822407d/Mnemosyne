## X-1 · "模型负责计算，文件负责记忆"还算不算硬原则

**旧话（2026-05-24，主线首对话交接包，逐字）**：
> "核心类比是现代计算机架构：模型像 CPU……外部文件 / GitHub 仓库 / 本地 Markdown / 数据库像硬盘：保存长期状态和事实……一句话概括：模型无状态化，记忆文件化，行为规则化，交接标准化，评估可复核化。"

当时的理由（RAW-0011 §10 保存的说明）：把模型从长期状态源中剥离——模型可升级替换、对话可重启、工作可交接、长期状态外部可见可审计可迁移；内部 memory 只当 cache。该类比现为执行源 §2 第一原则。

**新话（2026-08-30 消息一，逐字）**：
> "我针对'对话/任务上下文的记忆容量有限'构想出的'类冯诺依曼'架构只是一种想法,因此不应作为绝对的架构设计原则(很显然我在AI方面尤其是像gpt和claude这类LLM方面没有任何的专业知识,因此我这种牵扯到具体模型实现方案的构想没有任何依据,而没有依据的东西显然不能成为执行源)."

**为什么要现在澄清**：这是重新设计的地基。021/023 号研究显示：逐字外部保存有强实证优势（支持文件式）；但业界主流是多层混合（平台原生记忆＋检索＋文件），平台原生连续层 2026 年也成熟了不少。若该原则降级，阶段 2 可以让"文件式"与"混合式"按证据同台竞争；若保留硬原则，阶段 2 只在文件式框架内优化。

**选项**：A. 降为"有证据支持的默认方案"，允许被更强证据推翻（与你 8/30 的分级逻辑一致）；B. 保留为硬原则（外部文件永远是唯一长期真相源）；C. 你另有表述。
（答 A → 设计报告会出现混合架构候选并逐项给证据；答 B → 不再讨论替代，只优化；不答 → 按 A 假设推进并标注依赖。）

## X-3 · "记录越多越好"与"默认不读/输出压缩"的关系（确认一个读法）

**两段原话**：
- 2026-08-23（终审，逐字节选）："记录信息并不会增加多少运算和存储负担,能多记录些有关信息是最好的,唯一的问题就是信息可靠性"。
- 2026-08-11（Issue #265 评论，原文要点）：低频/一次性内容默认不进入运行读取集；"保存得越完整 ≠ 每次读得越完整"；普通解释优先自然语言、压缩用户大概率不读的输出。

**拟定读法（请确认或纠正）**：三句话不矛盾，分管三个面——**写入面尽量全（瓶颈只在可靠性）；读取面最小充分（默认不读，按需回查）；呈现面说人话（结构给机器、解释给人）**。若确认，"记录≠加载≠呈现"将作为阶段 2 的设计公理之一。
