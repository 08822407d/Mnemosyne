## 1. 问题拆解

两族共用 master 后有四个具体风险：

| 风险 | 真实案例锚点 |
|---|---|
| R1 过期起点：一族从旧 master 开工，覆盖/漏看另一族刚合并的内容 | MNEMOSYNE-150 并发对话撞车（两对话同任务重复建分支） |
| R2 生效延迟：A 族改了规则（guard/spec），B 族的进行中会话按旧规则继续跑 | loader 增长事件（199 结论未传导到 210/225 会话） |
| R3 写集冲突：两族的 open PR 触碰相同文件 | 单活跃 PR 防护是"每任务"级，跨族无路径交集检查 |
| R4 状态文件竞态：双方都要更新同一 live 状态文件（如注册表序号分配） | EXP-3 演练中两臂都自发识别了显示名注册表的串行化需求 |

## 2. 方案：四条轻量约定（零自动化，全部可并入现有 preflight）

### 约定一 · 写前拉最新、写完即推送（治 R1）

- 任何写入类会话的第一动作：fetch + pin 最新 origin/master（现行 preflight 已含，**升格为跨族强制**，写入尾注/记录的 base SHA 即证明）；
- 任何逻辑完整的变更完成即 push（Claude Code 已是惯例；ChatGPT 侧本就即时）；
- 会话跨越长时间（>数小时）再写时，重新 fetch 比对 pin——master 移动则重跑受影响的 preflight。

### 约定二 · 规则变更的"下会话生效 + 显式旗标"（治 R2）

- 生效模型明确化：**规则变更对"变更合并后新启动的会话"生效；进行中的会话不追溯**——避免会话中途规则漂移的混乱；
- 凡改变跨族共同规则（guard/spec/loader/署名惯例）的 PR，说明区块加一行 `cross_family_effective: yes` + 一句变更摘要；
- 对方族下次会话的指导加载天然读到新版（分层加载的 core 集必含变更载体）；紧急变更由 Owner 在下次启动指令里口头点名——不建推送通知机制（v0.1 无自动化）。

### 约定三 · 路径交集预检（治 R3）

- 现行谱系预检的 `by_equivalent_scope` 检查扩展一行：**枚举所有 open PR 的变更路径，与本任务 authorized paths 求交集**；
- 交集为空 → 正常并行（如 #306 与未来维护任务）；交集非空 → 停下四选一：等待合并 / 换路径 / 并入对方 lineage / 请 Owner 排序；
- 机械可查（gh pr diff --name-only），单命令成本。

### 约定四 · 共享计数器的"读-占-写同批"纪律（治 R4）

- 显示名序号、任务号、注册表条目这类共享计数器：分配动作必须"写前重读最新 → 在同一 PR 内落占位"，不得跨会话预留；
- 撞号处理从"预防"降为"检测+让位"：后提交者重读重分配（现实中交替工作撞号率极低，重防护不划算 [MODEL_INFERENCE]）。

## 3. 交接与生效的关系

族间工作移交 = 现行 handoff 协议原样适用（其跨族有效性已被本轨道 S1/S2/S4 重放与冷启动双重实证）；本方案不新增交接机制，只补"非交接式交替"（各做各的任务、共用 master）的空白。

## 4. 何时升级到 F2

出现以下任一情形，本轻量方案失效、F2（跨仓库/跨写者并发合同）成为前置门：两族需同时写同一仓库；出现共享 writer 服务；需要跨仓原子性。届时 F2 的 A1 验证按既定 Owner 门启动——与 Pro 裁定的 F2 定位完全一致。

## 5. 落地方式

全部四条并入现有文件，不新建 guard（响应"规则只增不减"教训）：约定一/三/四 → 谱系防护的 preflight 章节扩两行；约定二 → run-context 防护的 PR 披露字段加一行。归入实施任务 3（规范层改造）同批执行。

## 6. 自我批判

- 约定二的"不追溯进行中会话"在极端情形有漏洞：一个超长 Claude 会话可能按旧规则运行数天——对冲靠 Owner 口头点名与会话自身的定期 fetch，非机械保证；
- 路径交集检查对"语义冲突但路径不同"（两族改不同文件表达矛盾规则）无力——此类冲突只能靠异族抽检（D-08）兜底；
- 本稿由交替工作的一方起草，对"交替节奏假设"（同一时刻一族）的依赖未经长期验证；若 Owner 实际使用中频繁双线同开，应提前触发 §4 升级判断。
