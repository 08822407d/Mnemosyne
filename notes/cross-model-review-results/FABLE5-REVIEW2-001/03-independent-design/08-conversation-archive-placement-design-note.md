## 结论

**默认：一个专门的私有档案仓库统一存放；有严格数据隔离需求的业务项目允许例外自存；无论存哪，统一索引格式与引用规则；永不入公开仓库。**

## 四方案权衡

| 方案 | 判定 | 关键理由 |
|---|---|---|
| 统一存 Mnemosyne | 否 | Mnemosyne 公开（可见性致命）；对话不可能低成本全脱敏；Git 历史永久；且会把"设计工厂"撑成档案堆 |
| 各项目自存 | 不作默认 | 对话跨项目（族谱考古实证：主线对话同时处理多项目事务），硬切碎线索；评估需横扫 N 库 N 索引；档案性质（大体积、只增）污染工作仓库 |
| **专门私有档案库** | **默认采纳** | 一次解决可见性；一个命名空间一套索引（本轨道族谱索引即原型）；治理独立（只追加/免 PR 仪式）；寿命独立于项目仓库；顺带消除"档案仅存本机"单点（R2-SPOF-003/006） |
| 各有各的策略 | 受控例外 | 放任会重演状态文件散乱病；但数据隔离类例外合理，条件是共用索引格式与引用规则 |

## 设计要点

1. **结构**：`<项目>/<平台>/<对话文件>`（chatgpt/、claude-code/、codex/……格式异构容忍）+ 每项目一份索引（沿用本轨道已验证的逐件登记：日期/主线归属/任务号区间/交接事件/缺口/敏感档位）。
2. **敏感三档**：L0 可公开摘录 / L1 私有云端档案（默认） / L2 仅本地不推送；索引逐件记档。凭据/密钥任何档位不得入库（与可见性无关的铁律）。
3. **治理**：只追加、不改写历史；脱敏以"追加脱敏副本+墓碑注记"实现，不重写；直接提交即可（档案库无需工作仓库的 PR 仪式）——不同性质的仓库配不同重量的规矩（与规范层治理设计 A 的分级思想一致）。
4. **衔接**：工作仓库只存结晶（result record 惯例不变）+ 稳定指针（`档案库/项目/文件#锚点`）；公开仓库内最多脱敏摘录。
5. **迁移**：现 `~/projs/mnemosyne-archives/`（chatgpt 56 件+claude-code 快照+索引）整体成为新库首个工作副本，init+push 即完成。
6. **规模触发器**：MB 级纯文本 git 足够；未来若达 GB 级再议对象存储/LFS，现在不过度设计。
7. **复用价值**：本模式（分库+索引+族谱+引用+分档）本身是 Mnemosyne 可交付给目标项目的记忆系统底层设计件。

## 自我批判

- 集中即集中风险：私有库泄露=全泄露；对策依赖两条纪律（无密钥、L2 不上云）持续执行，无机械强制（v0.1 边界内接受）。
- "跨项目对话"论据来自 Mnemosyne 自身史；未来若各业务 Agent 对话高度自包含，各自存的硬伤之一会减轻——届时例外道可能扩大，默认不必改。
