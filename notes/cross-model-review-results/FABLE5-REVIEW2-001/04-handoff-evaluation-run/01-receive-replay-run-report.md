## 4. 归因发现（按 Owner 的四类失败来源分类）

### 4.1 活状态残留类（S1 实证，与阶段1 发现同根）
- [VERIFIED] S1 重放时点活状态文件确有 4 处残留（084 同日修复记录逐条列明：active-context 过期标题、todo 两处过期条目、open-questions 两处 pending 残留），而交接包自身准确。接收方"先核验再确认"的要求恰好构成对这类残留的检出机制——**协议有效，病灶在 live 层**。这与阶段1 的 R2-FRESH-001（状态失效纪律缺失）互为印证，且把该发现的时间起点推前到 7 月初：live 文件带病是贯穿全程的慢性病，不是 8 月才出现的。

### 4.2 交接件自身缺陷类（S4 报出 3 个真实协议缺陷，均为修复候选）
1. [VERIFIED_IN_ARTIFACT] **信息流不一致**：演练契约 002 直接携带了协议规定"只能来自 Startup Prompt 003"的 blob 期望值，且契约被交给接收方——供给渠道违反协议自己的信息流设计。
2. [VERIFIED_IN_ARTIFACT] **通用命令与路线协议冲突**：接收命令要求读 README，包却要求最小证据集且清单不含 README——接收方必须自行裁量，两个"必须"打架。
3. [VERIFIED_IN_ARTIFACT] **术语未定义**：F2/V2-A/A1/G2A/controller 在交接材料与执行源中均无定义，接收方只能从字段名反推——对协议要求的"fresh 接收方"构成理解税。
另有一项跨样本共性：**交接件无新鲜度字段**（S1 明确报出；S2 的 master 声明也只能标 unverified）——与阶段1 时效钩子缺失（修订案文 7）同根。

### 4.5 跨样本结构发现
- [VERIFIED] **包是指针不是容器**：三个样本的接收方分别列出 14/11/9 份"完成核验必需但切片外"的文件——交接包设计为"携带最小状态+指向证据"，其"最小充分"隐含**仓库完全可达**假设。受限环境（离线、权限受限、历史重放）下必然退化为 unverified 基线 + fail-closed。这是设计取舍而非缺陷，但应在协议中显式声明该假设。
- [VERIFIED] **平台假设硬编码**：三代交接件全部指定 ChatGPT 接收方（S1"new ChatGPT conversation"、S2"ordinary ChatGPT chat"、S4"fresh ChatGPT Pro"）。跨族接收方只能类推适用。为多写入方常态化束（束6）再添一条直接证据。
- [VERIFIED] **协议重量三代递增**：S1 无接收命令（2 件交接件）→ S2 增接收命令+规定首响应格式 → S4 增 canonical schema+演练契约+机械验收+11 项禁止清单。安全边际随真实失败教训增厚（S4 的修复即因两次接收失败），但 S4 的刚性 schema 在缺一件输入时即全阻断——安全与可用的取舍已到达值得 Owner 显式权衡的位置。[DESIGN_RECOMMENDATION] 供 Pro 检讨与合作方案参考：协议分级（高危路线用 S4 级刚性、普通维护用 S2 级）可能优于单调加重。
