## 5. Stage-A-only candidates

### B-NEW-001 — authority class and state/provenance contract

**Verdict: ACCEPT_WITH_MODIFICATION, P1 design.**

The problem is real. The migration draft currently calls `decision-log`, `core-object-model`, `requirement-intake-workflow`, and handoff material part of “Canonical Memory” beside the sole execution source, without authority-class fields. The object and template files also use inconsistent lifecycle and sensitivity semantics.

Required direction:

- retain `current/human-approved-spec.md` as the sole execution source;
- add explicit authority class to migration and reusable record schemas;
- separate lifecycle state from sensitivity;
- require decision evidence, actor, time, scope, affected version, and adjacent unapproved actions;
- do not introduce a factored operative set in the first repair.

### B-NEW-002 — prevention-first safety intake

**Verdict: ACCEPT, P1 immediate repair.**

The current generic Raw template allows `original_text` capture before a mandatory repository-visibility and sensitivity preflight. This is inconsistent with execution-source safety rules and the more specific target dry-run manifest.

Required direction:

- preflight before capture;
- unknown visibility/sensitivity uses public-risk treatment;
- secrets and credentials are absolute blockers;
- unsafe originals stay outside Git;
- pointer metadata is itself screened;
- Git-history persistence and residual re-identification risk are explicit.

### B-NEW-003 — target and delivery gates

**Verdict: ACCEPT_WITH_SCOPE_SPLIT, P1 contract propagation; P2 lifecycle redesign.**

The current target manifest already encodes strong approvals, while the generic delivery workflow is only `Intake → ... → Activate → Monitor → Iterate`.

Immediate part:

- generic runbooks must reference the strong approved manifest;
- workspace creation, material intake, real run, delivery, and target write remain distinct gates.

Later design part:

- define stage objects, entry/exit criteria, failure states, rollback, partial delivery, and activation authority.

### B-NEW-004 — platform permission, task authority, and action risk

**Verdict: ACCEPT_WITH_SPLIT, P1 stable contract; research-gated live mechanics.**

The stable contract is already approved and can be propagated now:

- platform capability is not task authority;
- repository, branch, path, protected paths, action risk, and current approval are explicit;
- persistent platform permission is never future task authorization.

The live capability chain—plan, role, workspace, install, enable, auth, sync, permission, action controls, approval mode, invocation—must remain research-gated.

### B-NEW-005 — user output contracts

**Verdict: ACCEPT, P2.**

The execution source already contains action-block, file-first/chunking, Deep Research body, and dependency-aware staging rules. The gap is downstream runbook labeling and duplication. This is current-document repair, not Greenfield adoption.

### B-NEW-006 — raw fidelity and similarity/delta comparison

**Verdict: ACCEPT_WITH_MODIFICATION, P2.**

Add evidence-preserving compilation and explicit same/delta/conflict/implementation-impact output. Do not silently choose raw depth, retention, or near-duplicate thresholds.

### B-NEW-007 — artifact existence versus capability

**Verdict: ACCEPT, P2 evidence hygiene.**

Documents, guards, and historical PASS records do not prove current runtime capability. Operational claims require pinned reproducible evidence or must be labeled document-only/unknown.

- authority class;
- lifecycle state;

- actor/provenance;

### C-10

- approved current policy;
- future branch parameter;

It must remain non-execution source and must not turn deferred defaults into policy.
