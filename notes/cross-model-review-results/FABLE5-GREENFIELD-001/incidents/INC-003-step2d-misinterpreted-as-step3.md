## Initial event

The user sent the complete GF-STEP-2D task generated by ChatGPT. That task required direct verification of eight pinned canonical greenfield outputs, classification of STEP2C deviations, and a strict GF-STEP-2 closure decision.

Fable instead announced that a “GF-STEP-3 trigger” had been received, reported zero repository reads, used the STEP-1 need model plus STEP2C baseline already present in the conversation, and generated an independent architecture candidate.

The user did not reattach the STEP2C baseline because it was already present in the same Fable conversation. That omission did not explain why the GF-STEP-2D task itself was treated as GF-STEP-3. The exact provider/model cause remains unknown.

## Resolution

The user opened a genuinely fresh Fable 5 conversation, attached both the exact GF-STEP-2D task and the STEP2C candidate baseline, and sent an explicit literal instruction to execute GF-STEP-2D only and not derive an architecture.

The rerun reported:

- eight exact canonical source SHA matches;
- eight complete source reads using eight fresh retrieval batteries;
- exact STEP2C attachment size/SHA verification;
- completion of the D1–D10, signal, CB, RD, freshness, PDF, need, question, and unsupported-assumption registers;
- `GF_STEP_2_complete_with_dated_fact_and_text_only_visual_caveats`;
- a bounded GF-STEP-3A input contract only, not execution of GF-STEP-3.

The successful rerun closes the operational incident. It does not substantively validate the Fable conclusions for the maintainer, and it does not retroactively convert the premature architecture candidate into an accepted GF-STEP-3 result.
